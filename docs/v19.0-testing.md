# OrangeHRM 19.0 testing

## Scope and source decision

Debian 13 Trixie does not package OrangeHRM. OrangeHRM 19.0 therefore uses
the official OrangeHRM 5.9 release asset from GitHub. The build pins the asset
URL and SHA-256 digest
`f6e640f8b59e8d09f15edcd24ac3d42bb52dcc4839a7d83f964dd798bc793f79`.
GitHub's official release metadata publishes the same digest. OrangeHRM 5.9
supports PHP 7.4 through 8.5 and MariaDB 5.5 through 12.0. Trixie's PHP 8.4
and MariaDB 11.8 are within that upstream support matrix.

Apache, PHP, MariaDB, Adminer and Postfix come from signed Debian Trixie
repositories. Webmin and its application modules come from the signed TurnKey
Trixie repository.

The maintained application update path is `orangehrm-update VERSION`. It
accepts only a newer stable version, reads the asset URL and SHA-256 digest
from the official GitHub release API, verifies the download, checks that the
target advertises a migration from the installed version, backs up the
database and application, runs the official noninteractive upgrader, and
swaps the application only after migration succeeds. `orangehrm-update
--check` inspects the current stable release without changing the appliance.
The release marker changes only after Apache restarts and the updated HTTP
endpoint passes its health check.

OrangeHRM 5.9 asks the server to run `php bin/console
orangehrm:run-schedule` every 5 to 15 minutes. The appliance runs that command
as `www-data` every five minutes from `/etc/cron.d/orangehrm`.

## Cheap probes

The official v5.9 GitHub release API returned asset
`orangehrm-5.9.zip`, size 22,228,229 bytes, with SHA-256 digest
`f6e640f8b59e8d09f15edcd24ac3d42bb52dcc4839a7d83f964dd798bc793f79`.
A disposable Trixie probe downloaded that asset and verified the digest. Local
archive inspection confirmed the official noninteractive installer and upgrade
command, PHP 8.5 maximum, MariaDB 12.0 maximum and 5.9 migration. The probe
installed OrangeHRM with MariaDB, loaded the login page, authenticated with a
strong firstboot-style password, opened the dashboard, migrated the legacy
password hash to bcrypt, and created, read and deleted an employee through the
application API. An initial installer attempt exposed the missing PDO MySQL
extension; adding `php-mysql` to the appliance plan resolved it. A second fresh
installation confirmed that OrangeHRM seeds
`auth.password_policy.enforce_password_strength` to `on` in `hs_hr_config` and
that the firstboot update changes that row to `off`.

The official v5.8.1 GitHub release API returned asset
`orangehrm-5.8.1.zip`, size 22,140,234 bytes, with SHA-256 digest
`72ffc4bdc465a4072e51581288c6880f05a50eccf17e53202299b59992ffa465`.
The fixture verifies this digest before installing 5.8.1. OrangeHRM 5.9
advertises and implements a migration from 5.8.1. The real disposable upgrade
result is recorded with exact acceptance evidence below.

## Known limitations

Docker runtime validation does not exercise the installer, kernel, bootloader
or physical hardware. OrangeHRM adds no appliance-specific behavior at those
boundaries, so the validated Core 19 baseline supplies inherited evidence.
The Docker kernel also rejects the hostname firstboot call and the
`systemd-sysctl` unit. The harness checks the application services explicitly.

The runtime check creates, reads and deletes an employee. It does not exercise
external SMTP delivery because that requires an external mail system.

The firstboot password remains governed by TurnKey's firstboot policy. The
appliance disables OrangeHRM's separate login-time strength redirect so the
password selected during appliance initialization grants the documented admin
access.
